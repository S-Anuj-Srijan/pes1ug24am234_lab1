# Complete Requirements Table

## Functional requirements

| ID | Type | Description | Priority | Acceptance criteria | Rationale |
|---|---|---|---|---|---|
| FR-001 | Functional - Jira task access | The system shall synchronize Jira tickets assigned to a remote developer and allow the developer to select an active ticket when creating a time entry. | High | **Pass:** An assigned active Jira ticket is retrieved and selectable with its key and summary; an unassigned or closed ticket is not selectable. **Fail:** A developer can log time against an unassigned or closed ticket. | Linking every entry to authorized project work improves traceability and prevents miscoding of effort. |
| FR-002 | Functional - Time entry | The system shall allow a developer to create, edit, and delete a draft time entry containing a work date, Jira ticket, duration, and work note, while preventing the developer's entries from exceeding 24 hours on any calendar day. | High | **Pass:** A valid entry is saved and an edit bringing the daily total to exactly 24 hours succeeds; an operation bringing it above 24 hours is rejected with an explanatory message. **Fail:** A daily total of 24.01 hours or more is saved. | Accurate, bounded entries are the basis of trustworthy timesheets, budgets, and approvals. |
| FR-003 | Functional - Timesheet submission | The system shall allow a developer to submit a weekly draft timesheet to the responsible engineering manager only when all entries are valid, and shall lock the submitted entries against developer editing until the manager rejects the timesheet. | High | **Pass:** A valid draft changes to **Submitted**, records submission time and manager, and becomes read-only. An invalid draft remains editable and lists validation errors. **Fail:** An invalid timesheet is submitted or a developer edits a submitted entry. | A controlled state transition gives managers a stable review record and prevents concurrent changes. |
| FR-004 | Functional - Approval workflow | The system shall allow the responsible engineering manager to review entry details and either approve a submitted timesheet or reject it with a mandatory comment; the system shall record actor and timestamp and notify the developer of the result. | High | **Pass:** Approval changes **Submitted** to **Approved** and notifies the developer; rejection without a comment is blocked; rejection with a comment changes the state to **Rejected**, unlocks the entries, and notifies the developer. **Fail:** An unauthorized manager acts, an invalid transition occurs, or a rejection has no comment. | Auditable decisions and actionable feedback support accountability and timely correction. |
| FR-005 | Functional - Budget monitoring | The system shall calculate actual labor cost from approved time and configured rates, display used amount, remaining amount, and burn percentage per project, and alert its engineering manager when burn first reaches or crosses 80% or 100% of budget. | Medium | **Pass:** For a budget of INR 100,000 and approved cost of INR 80,000, the dashboard shows 80% used and INR 20,000 remaining and emits one 80% alert; later crossing 100% emits one 100% alert. **Fail:** Draft/rejected time affects actual cost, figures are incorrect, or duplicate alerts occur for the same threshold crossing. | Early, accurate visibility lets managers correct overspend before it becomes irreversible. |

## Non-functional requirements

| ID | Type | Description | Priority | Acceptance criteria | Rationale |
|---|---|---|---|---|---|
| NFR-001 | Performance | Under a simulated peak load of 200 concurrent users, 95% of time-entry saves, approval status transitions, and budget-dashboard refresh requests shall complete within 500 ms, and 99% shall complete within 1 second, measured at the server boundary over a 30-minute test. | High | **Pass:** A repeatable load test with 200 concurrent users for 30 minutes meets both percentile targets with an error rate below 1%. **Fail:** Any percentile target is missed or the error rate is 1% or higher. | Remote teams need responsive interactions, especially around weekly submission deadlines. |
| NFR-002 | Security | The system shall enforce authenticated, role- and project-scoped access; use TLS 1.3 for data in transit and AES-256 or an equivalent approved algorithm for sensitive data at rest; and retain immutable audit events for time-entry and approval changes for at least 365 days. | High | **Pass:** Security tests show developers cannot access another developer's entries, managers cannot approve projects they do not manage, plaintext transport is rejected, protected storage is encrypted, and sampled audit events contain actor, action, target, and timestamp and cannot be altered by application users. **Fail:** Any unauthorized access succeeds, plaintext traffic is accepted, protected data is unencrypted, or a required audit event is missing/editable. | Timesheets contain sensitive employee and financial data, and approvals require defensible audit history. |

## Requirement quality notes

- Each requirement is uniquely identified, testable, and limited to one coherent capability or quality goal.
- “Calendar day” in FR-002 uses the developer's configured project time zone.
- A “week” in FR-003 uses the project's configured work-week boundary.
- Currency rounding in FR-005 uses the project's configured currency and two decimal places.
